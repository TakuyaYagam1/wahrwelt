# Updates, cleanup & recovery

[← Linux guide](../README.md)

Start with `nixos-update` for routine updates and `cleanup` for routine
garbage collection. This page covers what they change and how to investigate
a failed update.

## Update the installed system

Update the installed system with:

```bash
nixos-update
```

`nixos-update`, `nixy update`, and the TUI action **Update installed system**
use `wahrwelt update`. It reads the saved settings of the installed host,
updates Wahrwelt-owned fields in `flake.nix`, updates the lock, and builds
the system before publishing the files and switching. Custom inputs, local
modules, outputs, and comments are preserved. The TUI update action keeps
edits made during the current session for a later **Apply**; it does not run
the installer's dotfile sync.

Dotfile updates run during Home Manager activation. See
[what updates change](user-space.md#what-updates-change) for user files,
merge conflicts and migration of existing Neovim configurations.

For the first update from an older installation, run the fresh updater once:

```bash
nix run --refresh 'github:TakuyaYagam1/wahrwelt?dir=Linux/NixOS#wahrwelt' -- update
```

This also works when the old `nixos-update` fails while evaluating the host
flake, such as after the Zen input change. The old shell command cannot
upgrade its own update logic. After the new system is activated,
open a new shell so `nixos-update` loads the updated function and uses the
same updater for subsequent releases.

The updater follows the Wahrwelt source selected by the installed wrapper.
That source must currently use a literal `github:` URL; custom inputs can
keep their own source types.
Use `update --dry-run` to see proposed managed-field changes, or
`update --no-switch` to build the proposed system without publishing the
wrapper, lock, or migration state and without switching the system.

Default thin installs use an independent host lock: `/etc/nixos/flake.lock`
owns nixpkgs, Home Manager, Stylix, Quickshell, shell flakes, and the selected
Wahrwelt source revision. The `stable` channel uses the `main` branch; the
`development` channel uses `dev`. Updates of managed thin installs change
only the `wahrwelt` input by default and reuse the selected preset's
transitive lock shipped by Wahrwelt. Host-owned Lanzaboote stays pinned
unless named explicitly with `wahrwelt update lanzaboote`.

The file `/etc/nixos/wahrwelt-flake.json` records the managed fields last
installed by Wahrwelt. Updates compare these values with the current file
and the new defaults. Unmodified managed fields can be added, updated, or
removed; independent user edits are preserved. If both the user and Wahrwelt
changed a field differently, the update reports the conflict and leaves the
installed files unchanged. A retired input with remaining custom references
requires explicit resolution before removal.

Older wrappers without this record use migrations for recognized released
values. The `Generated by Wahrwelt` comment alone does not grant ownership
of the whole file. Unsupported expressions or conflicting edits need to be
resolved explicitly; an existing wrapper is never replaced wholesale.

Update preparation happens in a staging copy. Failed reconciliation or
builds leave the installed files untouched. Before publication the updater
checks for concurrent changes and retains a backup for recovery. Changes to
the package preset, Secure Boot, or other saved settings still go through
**Apply**, which uses the same reconciliation for the wrapper.

## Cleanup and build cache

Routine garbage collection in Fish:

```bash
cleanup
```

`cleanup` runs `nixy gc`. It removes user and system generations older than
`wahrwelt.nix.gcRetention` (14 days by default), keeps the current generations,
and preserves available build dependencies of retained store paths. Store
optimisation deduplicates identical files. Automatic garbage collection also
preserves build dependencies by default through `nix.settings.keep-outputs`.
This uses more disk space but avoids repeatedly rebuilding intermediate outputs,
such as Fish completions. It does not restore cache that was already deleted.

For a full cleanup:

```bash
clean-full
```

`clean-full` runs `nixy gc-full`. It deletes old user and system generations
and collects unused build outputs with `keep-outputs` disabled for that run.
Current generations and other GC roots remain protected. Old generations are
no longer available for rollback, and later builds may download or rebuild
their dependencies. Neither command updates packages or switches the system.

## Recovery

The installer creates a unique `/etc/nixos.bak.<timestamp>.<pid>.<n>` backup
before replacing `/etc/nixos`. A root-owned marker authenticates backups made
by current releases, and a successful activated apply keeps the newest three
authenticated backups. Historical unmarked backups and the displaced
`/etc/.nixos.migration.<suffix>` tree are never adopted or deleted
automatically. Review and remove those old copies manually only after the
updated system and the next `nixos-update` both succeed.

To recover manually, first identify a backup you want to restore:

```bash
ls -dt /etc/nixos.bak.*
```

Replace `BACKUP` with that directory and the timestamp in `CURRENT_RECOVERY`
with a unique value. Run the following block in Bash. It retains the current
tree before restoring the backup and stops if a check or command fails:

```bash
(
set -eu
BACKUP='/etc/nixos.bak.<timestamp>.<pid>.<n>'
CURRENT_RECOVERY=/etc/nixos.before-manual-recovery.YYYYMMDD-HHMMSS
sudo test -f "$BACKUP/flake.nix"
sudo test ! -e "$CURRENT_RECOVERY"
sudo test ! -L "$CURRENT_RECOVERY"
sudo cp -a --reflink=auto -- /etc/nixos "$CURRENT_RECOVERY"
sudo test -f "$CURRENT_RECOVERY/flake.nix"
sudo rsync -a --delete --delete-excluded --exclude=/.wahrwelt-backup-v1 "$BACKUP/" /etc/nixos/
sudo nixos-rebuild switch --impure --flake /etc/nixos#NixOS
)
```

Use your configured host output instead of `#NixOS` if it has a different name.
Keep `CURRENT_RECOVERY` until the rebuilt system and the next update both
succeed. It contains files that were newer than the selected backup and would
otherwise be removed by `rsync --delete`.

Run Doctor for checks and recovery hints:

```bash
wahrwelt doctor
```

For shell-switch issues, inspect:

```bash
test -n "${XDG_RUNTIME_DIR:-}" && cat "$XDG_RUNTIME_DIR/wahrwelt-shell.log"
```

There is intentionally no `/tmp` fallback. If `XDG_RUNTIME_DIR` is unset or
unsafe, the shell runtime fails closed and preserves the colliding path.

## Troubleshooting

Quick triage for the most common breakage paths. If none of these apply,
run `wahrwelt doctor` and check the relevant log.

- **Shell-swap (Super+Shift+W) does nothing or freezes.** Check
  `$XDG_STATE_HOME/wahrwelt/active-shell` (should be one of `caelestia`,
  `noctalia`, `end4`, `end4-pc`). Tail
  `$XDG_RUNTIME_DIR/wahrwelt-shell.log` while you press the binding. If the
  log reports a stale lock or ownership collision, run `wahrwelt doctor`,
  preserve any reported recovery path, and re-apply the selected profile.
  Do not remove the whole `hypr-runtime/` directory.
- **Hyprland keybinds are listed but do nothing.** Run `hyprctl configerrors`
  first. On Hyprland 0.55+, dispatch commands must use the Lua dispatcher API;
  Wahrwelt binds should go through `lib/wahrwelt.lua` helpers or direct
  `hl.dsp.*` calls, not old `hyprctl dispatch movewindow l` style strings.
- **Thunar shows generic icons instead of image previews.** Check that
  `tumbler` is running (`pgrep -f tumbler-1/tumblerd`), that
  `~/.cache/thumbnails/normal/` is writable, and that `XDG_DATA_DIRS`
  contains `/run/current-system/sw/share` and `~/.nix-profile/share`. If end4
  is active, this is most likely upstream `env = XDG_DATA_DIRS,...` leaking
  through - re-apply and re-login.
- **`apply --no-switch` fails at dry-build.** Read the Nix error tail; the
  installer aborts before touching `/etc/nixos`. Re-run
  `make -C Linux/installer nix-hm-eval` to localise the failure to a single
  module before retrying apply.
- **Build is huge / slow on first apply.** Expected: the config pulls in
  multiple Wayland shells, Qt/QML, desktop apps, optional CTF stacks. Check the
  [binary cache settings](install.md#binary-caches). A cache
  miss can still require a local build.
- **First `switch` fails after writing `/etc/nixos` with dbus/systemd activation
  errors.** Reboot into the new generation boundary, then run
  `sudo nixos-rebuild switch --impure --flake /etc/nixos#NixOS`. The dry-build already
  passed; this usually means the live system could not restart part of the
  desktop/session stack cleanly.
- **`sudo nixos-rebuild switch` works locally but `wahrwelt apply` fails.**
  The installer wraps switch with stricter checks (dry-build, password
  hash, dots mirror). Run `wahrwelt doctor` to see which precondition is missing.
